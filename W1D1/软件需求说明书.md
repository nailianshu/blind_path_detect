## 1 引言

### 1.1 编写目的

本文档定义盲道识别系统（Tactile Paving Recognition System，以下简称 TPRS）的**功能需求、性能需求、接口需求与运行环境要求**，作为后续系统设计、编码实现、测试验收的依据。

本文档的预期读者包括：

| 读者对象 | 关注章节 |
| :--- | :--- |
| 项目开发者 | 全部章节（重点 3、4） |
| 测试人员 | 3.1 功能需求、3.2 性能需求、5 验收标准 |
| 指导教师 / 评审专家 | 1、2、3.2、5、6 |
| 后续维护人员 | 4 运行环境规定、3.4 数据管理 |

### 1.2 项目背景

| 项 | 说明 |
| :--- | :--- |
| **系统名称** | 盲道识别系统（TPRS） |
| **系统形态** | Qt 6 桌面应用 + 深度学习推理引擎 |
| **核心技术** | 基于 YOLO 的实例分割（Instance Segmentation） |
| **开发语言** | C++17（应用层）/ Python 3.9（模型训练与验证） |
| **推理后端** | ONNX Runtime |

**问题背景**：视障人士依赖盲道出行，但现实中盲道普遍存在**被占用、被遮挡、破损、铺设中断或缺失**等问题。传统盲杖无法识别盲道的类型与走向，也无法感知前方是否存在障碍物，导致视障人士难以判断行进方向与风险。

**现有方案的不足**：

1. 传统图像处理方法依赖手工特征，对光照、角度、材质变化鲁棒性差；
2. 纯目标检测（bounding box）只能给出矩形框，无法刻画盲道的不规则走向与区域范围；
3. 缺少对盲道类型（行进 / 提示 / 停止）与异常状态（缺失、被占用）的区分能力。

**本系统的定位**：通过实例分割获得盲道的**像素级轮廓**，同时识别盲道类型、障碍物与盲道缺失区域，为视障人士提供可理解的方向引导与风险提示。

### 1.3 术语与定义

| 术语 | 定义 |
| :--- | :--- |
| **盲道（Tactile Paving）** | 铺设于人行道上、通过凸起纹理为视障人士提供触觉引导的设施 |
| **行进盲道** | 条形凸起盲道，提示"可沿此方向前行" |
| **提示盲道** | 圆点状凸起盲道，提示"前方有路口 / 转弯 / 需注意" |
| **停止盲道** | 位于站台、路口边缘，提示"到此停止，注意危险" |
| **盲道缺失** | 本应铺设盲道但实际未铺设、中断或严重破损的区域 |
| **实例分割** | 对图像中每个目标同时给出类别与像素级轮廓的任务 |
| **mAP@0.5** | IoU 阈值为 0.5 时的平均精度均值，衡量检测/分割精度 |
| **mAP@0.5:0.95** | IoU 阈值 0.5~0.95 步长 0.05 的平均值，更严格的精度指标 |
| **P95 时延** | 95% 的请求能在该时间内完成，用于衡量时延稳定性 |
| **ONNX** | 开放神经网络交换格式，用于跨框架部署模型 |

## 2 任务概述

### 2.1 系统目标

TPRS 的总体目标是：**在桌面端对图像 / 视频中的盲道进行实时分割与状态识别，并以可视化与语音方式向使用者输出引导信息。**

具体目标分解如下：

| 编号 | 目标 | 说明 |
| :--- | :--- | :--- |
| G-01 | 盲道区域像素级分割 | 输出盲道轮廓掩膜，而非仅矩形框 |
| G-02 | 盲道类型识别 | 区分行进盲道、提示盲道、停止盲道 |
| G-03 | 障碍物识别 | 识别盲道内 / 盲道上的障碍物（如交通锥） |
| G-04 | 盲道缺失检测 | 识别盲道中断、缺失区域 |
| G-05 | 实时性 | 端到端处理满足实时交互要求 |
| G-06 | 本地化部署 | 全部推理在本机完成，不上传用户图像 |

### 2.2 用户特点

| 用户类型 | 特征 | 对系统的要求 |
| :--- | :--- | :--- |
| **视障人士（主要使用者）** | 依赖听觉与触觉，无法操作复杂界面 | 语音播报清晰、界面极简、可一键启动 |
| **家属 / 陪护人员** | 有一定操作能力，需了解检测结果 | 界面可视化清晰、结果可回看 |
| **研究人员 / 开发者** | 需要调试模型与查看数据 | 提供参数配置、日志导出、模型切换能力 |

### 2.3 假定与约束

| 类型 | 内容 |
| :--- | :--- |
| **假定 A-01** | 输入图像为白天或光照充足的户外人行道场景 |
| **假定 A-02** | 摄像头视角为行进方向正前方，俯仰角在合理范围内 |
| **假定 A-03** | 盲道材质为国内标准规格（黄色 / 灰色凸起纹理） |
| **约束 C-01** | 系统须在**无网络**环境下可完整运行 |
| **约束 C-02** | 首期部署目标为 CPU 环境，不依赖独立显卡 |
| **约束 C-03** | 模型体积须控制在可随应用分发的范围内（≤ 50 MB） |
| **约束 C-04** | 数据集标注格式须兼容 YOLO 原生格式 |
| **约束 C-05** | 系统须运行于 macOS / Windows 桌面平台 |

## 3 需求规定

### 3.1 功能需求

#### 3.1.1 功能结构

```

├── F1 数据输入模块
│   ├── F1.1 图像文件输入
│   ├── F1.2 视频文件输入
│   └── F1.3 摄像头实时输入
├── F2 推理引擎模块

│   ├── F2.2 图像预处理

├── F3 结果可视化模块
│   ├── F3.1 分割掩膜叠加显示
│   ├── F3.2 类别标签与置信度显示
```

| :--- | :--- | :--- | :--- |

| PR-2.3 | 视频处理帧率 | ≥ 10 FPS | 视频文件模式 |
| PR-2.4 | 应用冷启动时间 | ≤ 5 s | 含模型加载 |

#### 3.2.4 灵活性要求

### 3.3 输入输出要求

#### 3.3.1 输入要求

| 项 | 要求 |
| :--- | :--- |
| 图像格式 | JPG / JPEG / PNG / BMP |
| 视频格式 | MP4 / AVI |
| 图像分辨率 | 支持 320×320 至 4096×4096，自动缩放至模型输入尺寸 |
| 色彩空间 | RGB / BGR 自适应转换 |

#### 3.3.2 输出要求

| 项 | 要求 |
| :--- | :--- |
| 可视化输出 | 原图叠加彩色分割掩膜 + 类别标签 + 置信度 |
| 结构化输出 | 每个目标：类别 ID、类别名、置信度、包围框坐标、掩膜轮廓点集 |
| 统计输出 | 各类别目标数量、单帧耗时 |
| 告警输出 | 语音提示文本 / 界面告警条 |

#### 3.3.3 检测类别定义

| 类别 ID | 类别名称 | 英文名 | 说明 |
| :--- | :--- | :--- | :--- |
| 0 | 行进盲道 | blind path / guiding paving | 条形凸起，指示行进方向 |
| 1 | 提示盲道 | warning paving | 圆点凸起，提示路口或转向 |
| 2 | 停止盲道 | stop paving | 提示到达边缘需停止 |
| 3 | 障碍物 | obstacle | 盲道内或盲道上的障碍物 |
| 4 | 盲道缺失 | missing paving | 盲道中断或未铺设区域 |

> **说明**：类别编号与 `data.yaml` 中的 `names` 顺序严格一致，模型输出类别 ID 直接映射至上表。

### 3.4 数据管理能力要求

| 需求编号 | 要求 |
| :--- | :--- |
| DR-1 | 训练数据须采用 YOLO 标注格式（`class x1 y1 x2 y2 ...` 多边形归一化坐标） |
| DR-2 | 数据集须按 train / valid / test 划分，比例建议 8:1:1 |
| DR-3 | 单次检测记录条目须包含时间戳、输入源、各类别计数、耗时 |
| DR-4 | 历史记录存储容量不少于 10 万条，超出后按时间滚动清理 |
| DR-5 | 所有数据均存储于本地，不得上传至外部服务器 |

### 3.5 故障处理要求

| 需求编号 | 故障场景 | 处理要求 |
| :--- | :--- | :--- |
| ER-1 | 模型文件缺失 / 损坏 | 弹出明确提示，禁用推理功能，应用不崩溃 |
| ER-2 | 输入文件无法读取 | 提示"文件无法读取"，保留上一次有效结果 |
| ER-3 | 摄像头被占用 | 提示设备占用，允许切换至文件模式 |
| ER-4 | 推理过程异常 | 捕获异常并记录日志，单帧失败不中断视频流 |
| ER-5 | 内存不足 | 降低输入尺寸或提示用户，避免强制退出 |

### 3.6 其他专门要求

| 需求编号 | 类别 | 要求 |
| :--- | :--- | :--- |
| OR-1 | 易用性 | 主界面操作路径不超过 2 层，核心功能一键可达 |
| OR-2 | 无障碍 | 界面文字支持大字号模式；告警须同时提供语音与视觉通道 |
| OR-3 | 可维护性 | 模块间低耦合，推理引擎须可独立替换 |
| OR-4 | 可移植性 | 推理后端基于 ONNX，不绑定特定硬件厂商 |
| OR-5 | 隐私安全 | 用户图像仅在本机处理，默认不留存原始图像 |
